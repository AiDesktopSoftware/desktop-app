# 工作模式「用户 DIY 工作流」设计报告

> 负责人：赵（RAG / Agent / 知识库 / 研究报告）
> 依据：现有 `src/main/work/` 代码与 `docs/rag-architecture.md`
> 核心导向：让用户尽可能 DIY 自己的工作流

---

## 一、结论先行

三句话概括：

1. **不推翻现有的 Agent，而是让它变成两种模式之一。** 现在的 `agent.ts` 是「模型自己决定调什么工具」，DIY 工作流是「用户自己决定调什么」。两者共用同一套节点注册表和执行器，可以并存。
2. **DIY 不是从零做一个 n8n，而是把已有的「能力注册表」升级成「节点注册表」。** `capabilities.ts` 已经是节点体系的雏形，缺的只有三样：输出类型、节点间数据传递、工作流定义与运行记录。
3. **第一版只做「模板 + 参数配置」，不做拖拽画布。** 画布的工作量是表单式的 5 到 6 倍，而研究类工作流 90% 是线性链路，画布带来的收益远小于它吃掉的时间。

---

## 二、DIY 到底 DIY 什么

「让用户 DIY 工作流」有四个层次，能力与成本差异极大，必须选一层作为边界：

| 层次 | 用户能改什么 | 用户感知 | 实现成本 | 判断 |
|---|---|---|---|---|
| L0 参数配置 | 改检索条数、模型、提示词 | 只是设置项 | 低 | 不算 DIY |
| L1 模板 + 参数 | 选一个预置流程，填自己的主题与来源 | 「我能配出我要的」 | 低 | **第一版做这层** |
| L2 流程可编排 | 自己增删节点、排序、连线、存成自己的流程 | 「我真的在搭流程」 | 中 | **目标层** |
| L3 节点可扩展 | 用户写代码或装插件造新节点 | 「这是平台」 | 极高 | 不做 |

**结论：做到 L2，用「线性流程编辑」而不是「自由画布」来承载。** 理由在第十节展开。

---

## 三、现状盘点（基于真实代码）

已有资产比想象中多，这决定了 DIY 的起点不是零：

| 已有 | 位置 | 对 DIY 的价值 |
|---|---|---|
| 能力注册表 | `capabilities.ts` | 就是节点注册表的前身，已有 id / 说明 / 参数表单字段 / JSON Schema / 权限 |
| 统一执行入口 | `tools.ts` 的 `executeTool` | 就是节点执行器的前身，已做异常兜底与统一返回结构 |
| 单能力试跑通道 | IPC 的 `runCapability` | 就是「单节点调试」，DIY 产品最关键的体验已经有一半 |
| 事件推送模式 | `work:agent:tool` / `work:evidence` | 可直接复用来做「按节点的运行进度」 |
| 中止机制 | `AbortSignal` 全链路贯通 | 可直接复用来做「停止运行」 |
| 检索方案 | `docs/rag-architecture.md` | 节点库里的「检索」节点已有明确设计 |
| 会话持久化 | `store.ts` + `WorkSession` | 工作流持久化可照抄这套模式 |

缺口只有四个，都集中在「节点之间」：

| 缺口 | 后果 |
|---|---|
| 没有输出类型声明 | 用户不知道一个节点的输出能不能接下一个节点 |
| 没有节点间数据传递 | 现在每次工具调用都是模型临时拼参数，无法串成流程 |
| 没有工作流定义与运行记录 | 流程无法保存、复用、分享、复现 |
| 能力偏「系统工具」 | 现有 6 个能力是搜索 / 抓取 / 读写 / 命令，缺少研究型节点（检索、摘要、报告） |

## 四、核心判断：双模式并存，而不是替换

| 模式 | 谁决定执行顺序 | 特点 | 适用 |
|---|---|---|---|
| 自动模式（现有） | 模型 | 灵活、不可复现、每次不一样 | 探索式提问、临时任务 |
| 编排模式（新增） | 用户 | 确定、可复现、可保存、可分享 | 固定套路的调研、周报、综述 |

**关键设计：两种模式共用同一个节点注册表和同一个执行器。** 自动模式是「模型在运行时挑节点」，编排模式是「用户在编辑时排节点」。这样做的收益：

- 现有 `agent.ts` 一行不用改，风险最低；
- 用户先在自动模式跑一次，觉得好用，点「保存为工作流」把这次调用序列固化成编排流程 —— 这是最好的 DIY 入口；
- 答辩时可以现场对比：同一个任务，自动模式每次结果不同，编排模式每次一致 —— **这就是 DIY 价值最直观的证明**。

## 五、地基：工作流定义契约

这是整个 DIY 系统的地基，比三人之间的 API 约定更重要，因为它定义了节点之间的数据怎么流。定义分四部分：

### 5.1 元信息

| 字段 | 说明 |
|---|---|
| 工作流 ID / 名称 / 描述 | 用于列表展示与分享 |
| 版本号 | 工作流本身也要能演进 |
| 是否模板 | 区分「系统预置」与「用户自建」 |
| 创建者 / 创建时间 / 最近运行时间 | 展示与排序 |

### 5.2 节点

| 字段 | 说明 |
|---|---|
| 节点 ID | 流程内唯一，用于被下游引用 |
| 节点类型 + 版本 | 如 `retrieve@1`，节点升级后旧流程仍可识别 |
| 显示名 | 用户可改，如「检索政策文件」 |
| 参数 | 键值对，来自节点类型的参数定义，用户可改 |
| 输入绑定 | 每个输入端口接到哪个上游节点的哪个输出端口 |
| 失败策略 | 终止 / 跳过 / 重试一次 |

### 5.3 边

只描述「源节点.输出端口 → 目标节点.输入端口」。第一版只支持无环有向图，不做循环。

### 5.4 运行时变量

与节点参数区分开，这是 DIY 体验的关键：

| 类型 | 例子 | 谁填、什么时候填 |
|---|---|---|
| 静态参数 | 检索条数 = 5 | 编辑流程时填，存进流程 |
| 运行时变量 | 研究主题、时间范围、指定来源 | 每次运行前由用户填写 |

**这个区分必须从第一版就做。** 否则用户每换一个研究主题就要改一遍流程，DIY 就变成了「改配置」，体验会很差。

## 六、节点契约：从「能力」升级为「节点」

现有能力定义已经具备参数侧的一切，缺的是数据侧。升级清单：

| 现有字段 | 处理方式 |
|---|---|
| `id` | 保留，增加类型与版本的概念 |
| `label` / `description` | 保留，直接用作节点显示名与说明 |
| `fields`（表单字段） | **直接复用**，这就是节点参数表单，前端不用再设计一套 |
| `paramsSchema` | 保留，用于参数校验与自动表单 |
| `permission` | 保留，用于判断节点是否需要用户确认 |
| `agentEnabled` | 改为「是否允许自动模式调用」，两个模式各一份白名单 |

必须新增的五个字段：

| 新增字段 | 作用 |
|---|---|
| 输入端口 | 名称 + 数据类型 + 是否必需 |
| 输出端口 | 名称 + 数据类型 |
| 副作用标记 | 是否联网 / 是否写文件 / 是否执行命令 / 是否花钱 |
| 耗时预期 | 用于前端提示与超时设置 |
| 引用产出 | 该节点是否会产生可溯源的来源信息 |

其中「副作用标记」不只是好看：编排模式下一键跑整条流程，如果中途有写文件或执行命令的节点，必须让用户确认，否则是安全事故。

## 七、第一版节点库（8 个）

不要一上来做通用节点平台，只做这条业务链需要的节点：

| 节点 | 输入 | 输出 | 归属 | 说明 |
|---|---|---|---|---|
| 数据加载 | 来源条件、时间范围 | 文档数组 | 胡的数据 / 赵实现 | 消费胡的 JSONL 或本地库 |
| 检索 | 查询文本、条数、库选择 | 片段数组（带来源） | 赵 | 对接现有双通道检索方案 |
| 过滤 | 片段数组、条件 | 片段数组 | 赵 | 时间 / 来源 / 去重 / 截断 |
| 摘要 | 片段数组、目标长度 | 要点数组 | 赵 | 内部会调模型节点 |
| 模型调用 | 提示词模板、变量 | 文本 | 龙 | 参数暴露模型名、温度、长度 |
| 联网搜索 | 关键词、条数 | 结果列表（带链接） | 赵 | 复用现有 `web_search` |
| 网页读取 | 网址 | 正文 + 来源 | 赵 | 复用现有 `fetch_url` |
| 报告段落 | 标题、正文、引用集合 | 报告片段 | 赵 | 引用在这里汇总 |

时间充裕再加两个：**对比**（两组片段 → 对比结构）、**导出**（报告片段 → 文件）。

**第一个模板就叫「文献综述」**：数据加载 → 检索 → 过滤 → 摘要 → 报告段落。这条链能覆盖课设演示的绝大部分场景。

## 八、执行引擎

第一版刻意做小，只解决「按顺序把数据传下去」：

| 能力 | 第一版 | 说明 |
|---|---|---|
| 图结构 | 无环有向图 | 环检测在保存时就拦住 |
| 执行方式 | 拓扑排序后顺序执行 | 不做并行，够用且好调试 |
| 数据传递 | 运行上下文按「节点.端口」索引 | 下游通过引用取值 |
| 失败处理 | 终止 / 跳过 / 重试一次 | 用户可在节点上单独设置 |
| 运行记录 | 每次运行一条记录，每个节点一条子记录 | 存输入快照、输出快照、耗时、错误 |
| 进度上报 | 复用现有事件推送 | 前端渲染成节点状态树 |
| 长任务 | 异步运行 + 返回运行 ID | 前端订阅事件，可中止 |
| 断点调试 | 支持「只运行到第 N 个节点」 | 这是 DIY 能不能用的分水岭 |

最后一条最容易被忽略但最重要：**用户拼出来的流程第一次几乎一定跑不通**。如果不能单独跑某一段、看某个节点的中间结果，用户会直接放弃。现有 `runCapability` 通道已经证明单节点试跑是可行的，把它扩展成「运行到此处」即可。

明确不做的引擎能力：条件分支、循环、并行、子流程嵌套、定时触发。这些是 n8n 级别的功能，课设周期内做不完，而且会把调试复杂度推高一个量级。

## 九、DIY 真正的难点：数据在节点之间怎么流

这是整个方案最容易翻车的地方，比执行引擎本身难得多。四个必须提前想清楚的问题：

### 9.1 端口类型

给端口定一组极简类型即可：文档数组、片段数组、文本、要点数组、报告片段。规则：

- 连线时做类型兼容校验，不兼容直接拒绝并给出提示；
- 不引入复杂类型系统，不做泛型、不做结构体嵌套。

### 9.2 参数里的引用

节点参数要能写「引用上游节点的某个输出」。设计上必须区分三种值：

| 写法 | 含义 |
|---|---|
| 固定值 | 用户直接填的字面量 |
| 上游引用 | 取某个节点的某个输出端口 |
| 运行时变量 | 运行前由用户填写 |

解析顺序：先替换运行时变量，再解析上游引用，最后交给节点执行。

### 9.3 上游为空怎么办

这是 DIY 最常见的失败场景。三种策略要让用户在节点上选：

| 策略 | 行为 |
|---|---|
| 跳过 | 上游为空则不执行该节点，下游继续 |
| 空跑 | 用空输入执行，节点自己决定返回什么 |
| 终止 | 整条流程停止并报错 |

默认用「跳过」，因为它最符合用户直觉。

### 9.4 版本兼容

节点类型带版本号。节点升级后，旧工作流加载时要做两件事之一：自动迁移，或明确提示「该流程使用了旧版节点，需重新确认参数」。**不能静默失败**，否则用户存了一堆流程，某天全打不开，DIY 的信任就没了。

## 十、引用溯源：DIY 场景下从「加分项」变成「必需品」

在固定流程里，引用是产品的亮点；在 DIY 里，引用是产品的**信任基础**。

原因很直接：用户自己拼的流程，出了问题没人能负责。如果报告里每句结论都能点开看到「来自哪篇文档的哪一段」，用户才敢用；否则用户会怀疑是模型编的。

落地要求：**引用信息必须随数据在节点之间流动，而不是最后从文本里反向解析。**

| 环节 | 要求 |
|---|---|
| 检索节点 | 每个片段携带文档 ID、片段 ID、原文摘句、来源链接 |
| 摘要 / 模型节点 | 输出必须携带「用了哪些输入片段」，做输入到输出的映射 |
| 报告节点 | 汇总上游全部来源，自动生成参考文献列表 |
| 前端 | 每个结论旁可展开看到原文，点击可跳转来源 |

这一点现在的代码里已有基础：`WorkEvidenceItem` 和 `work:evidence` 事件已经在做「来源汇总」，把它从「按 URL 去重」升级为「按片段 ID 溯源」即可。

## 十一、前端策略：三级递进，先别做画布

| 级别 | 形态 | 工作量 | 用户感受 |
|---|---|---|---|
| L1 表单式 | 选模板 → 填参数 → 运行 → 看进度和结果 | 1 倍 | 能用，但不像「搭流程」 |
| L2 线性编辑 | 节点列表，可增删、上下移、改参数、看单节点结果 | 2 倍 | 真的在 DIY |
| L3 自由画布 | 拖拽节点、连线、缩放、撤销、实时校验 | 5 到 6 倍 | 像 n8n |

**建议做到 L2 为止。** 核心理由：研究类工作流的本质是「取数据 → 筛 → 分析 → 写报告」，天然是线性或浅分支，画布带来的表达力增量很小，但要付出连线交互、布局算法、缩放平移、冲突校验、撤销重做一整套成本。课设周期里，这部分时间应该花在检索质量和引用溯源上。

L1 的界面元素其实很少：模板卡片列表、参数表单（可直接用现有 `fields` 渲染）、运行按钮、节点状态树、结果区、引用面板。这些在现有工作模式页面里扩展即可，不需要新开一套框架。

## 十二、分期路线与 MVP 边界

| 阶段 | 目标 | 是否依赖队友 |
|---|---|---|
| P0 | 节点契约落地：给现有能力补输入输出端口与副作用标记 | 否 |
| P1 | 顺序执行器 + 运行记录 + 一个「文献综述」模板跑通（假数据、假模型） | 否 |
| P2 | 前端 L1：模板列表、参数表单、进度树、结果与引用 | 否 |
| P3 | 接真数据（胡的 JSONL）与真模型（龙的 OpenAI 兼容接口） | 是，但有适配层兜底 |
| P4 | 前端 L2：线性编辑、单节点试跑、保存为我的流程 | 否 |
| P5 | 加分项：自动模式「保存为工作流」、双模式对比演示、评测集 | 否 |

**MVP 边界 —— 明确不做：**

- 不做自由画布与拖拽连线
- 不做条件分支、循环、并行、定时触发
- 不做用户自定义代码节点与插件市场
- 不做自然语言一键生成工作流
- 不做多人协同编辑与流程分享平台
- 不做权限体系与多用户

这份「不做清单」要写进文档并对外说清楚，否则用户会按 n8n 的预期来要求，范围必然失控。

## 十三、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围蔓延成 n8n | 做不完，核心功能反而粗糙 | 把「不做清单」写死在文档里，评审时逐条确认 |
| 节点契约反复改 | 引擎和前端反复返工 | 先手写一条「文献综述」模板做纸上自检，确认契约自洽再写代码 |
| 端口类型缺失 | 用户连出跑不通的流程 | 第一版就强制类型声明与连线校验 |
| 用户拼的流程跑不通且无从排查 | 用户直接放弃 DIY | 必须支持单节点试跑与中间结果查看 |
| 引用在节点间丢失 | 报告不可信，产品价值崩塌 | 引用随数据流动，写进每个节点的输出契约 |
| 节点升级导致旧流程失效 | 用户存量流程全废 | 节点类型带版本号，加载时迁移或明确提示 |
| 前端编辑器吃光时间 | 检索质量与报告质量没做 | L1 起步，L2 为上限，L3 不做 |
| 演示缺乏说服力 | 答辩讲不出 DIY 的价值 | 保留自动模式，现场做「同一任务、两种模式」对比 |

## 十四、行动清单

1. 给现有能力补三个数据侧字段：输入端口、输出端口、副作用标记（不动执行逻辑）
2. 定工作流定义的四部分：元信息、节点、边、运行时变量
3. 用文字手写「文献综述」模板，纸上走一遍数据流，确认契约自洽
4. 实现顺序执行器与运行记录（工作流、运行、节点运行、引用四张表）
5. 复用现有事件推送做节点级进度，复用中止机制做停止运行
6. 前端 L1：模板卡片、参数表单、进度树、结果与引用面板
7. 接入胡的 JSONL 与龙的模型接口，各做一个适配层
8. 前端 L2：线性编辑、单节点试跑、「运行到此节点」
9. 补一个「自动模式 → 保存为工作流」的入口
10. 准备 20 条「问题 → 应命中片段」的评测集，用命中率证明检索质量

---

## 十五、一句话总结

**把「模型自己选工具」升级成「用户自己排节点」，共用一套注册表和执行器；节点做少做精，前端做到线性编辑就停，引用随数据流动，其余一律不做。**
