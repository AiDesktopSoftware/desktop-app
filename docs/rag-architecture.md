# 双通道 RAG 方案（本地私有库 + 云端公共库）

> 结论：**不做内网穿透，不买服务器。** 公共库走阿里云百炼的托管知识库 API，私有库在用户本机建，
> 两条通道共用一套「检索契约」，生成统一在本地 Agent 层完成。

---

## 一、方案要点

| 项 | 决策 |
|---|---|
| 内网穿透 | 放弃。frp / 自建 ECS 全部不再使用 |
| 公共 RAG | 阿里云百炼（Model Studio）托管知识库，调其**检索** API |
| 本地 RAG | 本机 Python 服务（仅监听 `127.0.0.1`）+ 本地向量库 |
| 嵌入模型 | 硅基流动 `BAAI/bge-m3`（OpenAI 兼容接口，有免费额度） |
| 生成模型 | DeepSeek（现在）→ 龙的本地模型服务（后续，OpenAI 兼容） |
| 向量存储 | SQLite + 向量扩展（单文件，随库目录走） |
| 统一原则 | **两条通道都只返回「检索片段」，不返回成品答案**，生成永远在本地做 |

---

## 二、架构

```
┌─────────────────────────── Electron 桌面端 ───────────────────────────┐
│  渲染层（Vue）                                                         │
│    工作模式：选择「本地库 / 云端公共库 / 双路合并」，展示证据与引用        │
│         │ IPC                                                          │
│  主进程（TS）：Agent 循环、任务拆解、提示词拼装、流式输出                 │
│         │                                                              │
│         ├── RetrievalProvider 统一接口 ──┐                              │
│         │                                │                              │
│         │        ┌───────────────────────┴──────────────────────┐      │
│         │        │                                              │      │
│         │   LocalRagProvider                          CloudRagProvider  │
│         │        │ HTTP 127.0.0.1                              │ HTTPS   │
│         │   ┌────▼─────────────┐                    ┌─────────────▼───┐ │
│         │   │ 本机 RAG 服务     │                    │ 阿里云百炼       │ │
│         │   │ Python + FastAPI │                    │ 托管知识库       │ │
│         │   │ 解析/切分/嵌入/检索│                    │ 检索 API         │ │
│         │   └────┬─────────────┘                    └─────────────────┘ │
│         │        │                                                      │
│         │   SQLite 向量库 + 原始文件                                     │
└─────────┴──────────────────────────────────────────────────────────────┘
                                │
                                ▼
                      生成：DeepSeek / 龙的模型服务
```

**关键点：**

1. 本地 RAG 是 `127.0.0.1` 上的回环服务，**不需要任何穿透**，但对上层仍然是一个 HTTP 接口——
   和云端库的调用形态完全一致，这是双通道能共用一套代码的前提。
2. 公共库只调「检索」而不是「问答」，因此**龙的位置没有被挤掉**：检索结果照样回流到本地生成环节。
3. 断网时本地库仍可用；云端库不可用时降级为本地库，界面如实提示。

## 三、技术选型

| 环节 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 公共知识库 | 阿里云百炼 | 国内直连、无需代理、有免费额度、检索 API 独立可调 | 扣子（检索能力弱，且三方库需公网连接器，正好是我们要避开的） |
| 嵌入 | 硅基流动 `BAAI/bge-m3` | OpenAI 兼容、中文效果好、有免费额度、国内直连 | 百炼 `text-embedding` 系列；本地 `bge-small`（隐私模式） |
| 向量库 | SQLite + 向量扩展 | 单文件、零服务、符合「能本地存储不用数据库」的偏好 | LanceDB（目录形态）、FAISS（仅索引，元数据要另存） |
| 本地 RAG 运行时 | Python + FastAPI | 解析 PDF/Word/网页的生态在 Python 最成熟；也符合课程对 Python 后端的要求 | 全 TS 实现（Node 解析能力弱，中文切分要自己造） |
| 生成 | DeepSeek → 龙的模型 | 均为 OpenAI 兼容，切换只改 baseUrl | — |
| 文档解析 | PyMuPDF / python-docx / BeautifulSoup | 覆盖课程里最可能出现的三类来源 | — |

> 本地 RAG 服务由 Electron 主进程在启动时拉起，端口随机分配后回写配置；进程退出时一并结束。
> 这是本方案**唯一增加**的运行复杂度，换来的是不重写一套 PDF 解析与切分。

## 四、统一检索契约（三人协作的核心）

### 4.1 赵的内部接口

| 字段 | 含义 |
|---|---|
| `query` | 检索问题 |
| `topK` | 返回片段数，默认 5 |
| `provider` | `local` / `cloud` / `both` |
| `filters` | 时间范围、来源类型、标签（可选） |

返回：片段数组，每项含 `chunkId`、`text`、`score`、`provider`、`source{title,url}`。

`both` 模式先各自检索，再按分数融合去重（阶段 P3 再做，P0–P2 只支持单选）。

### 4.2 胡 → 赵（离线文件，不走网络）

胡按 JSONL 交付，一行一篇，字段约定：

| 字段 | 必填 | 说明 |
|---|---|---|
| `docId` | 是 | 全局唯一，建议用来源 URL 的哈希 |
| `title` | 是 | 标题 |
| `content` | 是 | 清洗后的纯文本正文 |
| `sourceUrl` | 是 | 原文地址 |
| `sourceType` | 是 | `web` / `pdf` / `doc` / `manual` |
| `publishedAt` | 否 | 发布时间，缺失留空 |
| `collectedAt` | 是 | 采集时间 |
| `rawPath` | 是 | 原始文件相对路径 |
| `tags` | 否 | 主题标签数组 |

**两条通道的入库方式不同**，这是必须提前说清的分叉：

- **本地库**：直接消费 JSONL → 切分 → 嵌入 → 入本地向量库，全程离线可控
- **云端公共库**：需要把文档**上传到百炼知识库**（调其文档导入接口），格式需对齐百炼要求；
  入库动作是「发布」而非「同步」，因此**不能指望每采一篇就自动进公共库**

### 4.3 赵 → 龙

龙的服务按 OpenAI 兼容协议暴露 `/v1/chat/completions`，赵侧只改 `baseUrl`，RAG 链路不感知模型来自哪。
**这条边界现在不用动，属于低成本预留。**

## 五、必须澄清的一个概念

**「网站的公共 RAG」不等于「全网公共知识库」。**

百炼、扣子的知识库都托管在**你自己的账号空间**里，只有持有 API Key 的人能访问。所以本方案里的「公共」准确含义是：

> **全组共用同一个云端账号下的托管知识库，三人共享一套 Key。**

它解决的是「知识库不用每人建一份、不用跑在自己电脑上」，**不是**「任何人都能匿名使用」。
如果答辩要求「老师用自己的电脑访问」，那仍然绕不开一个对外可访问的服务——这属于被排除的部署问题，需要提前和老师确认口径。

## 六、分阶段计划

| 阶段 | 目标 | 交付 | 是否依赖队友 |
|---|---|---|---|
| P0 | 统一契约 + mock provider，前端做出「知识库来源」选择 | 界面可切换三种来源，返回假片段 | 否 |
| P1 | 本地 RAG 最小闭环：导入 1 份文档 → 切分 → 嵌入 → 检索 → 生成带引用 | 单文件可问答，证据面板显示来源 | 否 |
| P2 | 云端公共库接入：百炼建库 → 检索 API → 同一契约 | 切换后结果来自云端库 | 否（自建库自测） |
| P3 | 双路合并、证据链加固、研究报告导出 | 一次提问两库并检，报告可导出 | 否 |
| P4 | 生成环节切到龙的模型服务 | 只改配置即可切换 | 是（龙） |

P0–P3 全部可以独立完成，不等队友；胡的数据到了直接按 JSONL 灌入即可。

---

## 七、明确不做

- 不做内网穿透（frp、Grok 隧道、Cloudflare Tunnel 均不引入）
- 不买/不自建云服务器
- 不做「云端库端到端直接答」作为主链路（可作为快捷模式后续加，但不进主流程）
- 不做多用户账号与权限体系
- 不做在线协作编辑

---

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 百炼需实名开通、要拿 workspaceId | P2 卡住 | P0/P1 先做，不阻塞；提前在控制台开通并记录配置位置 |
| 嵌入免费额度有速率限制 | 批量建库失败 | 分批 + 退避重试；建库是一次性动作，可慢 |
| 演示现场断网 | 云端库不可用 | 本地库兜底；答辩前把演示文档预先灌进本地库 |
| 三人共享一套 Key | Key 泄露、额度被刷 | Key 只存主进程配置 / 本地配置文件（已 gitignore），界面只显示后四位 |
| Python 服务随应用启停 | 打包后进程管理复杂 | 端口随机 + 健康检查 + 退出清理；P1 先在开发态跑通再处理打包 |
| 本地向量库与文档不同步 | 检索到已删除内容 | 入库记录文件指纹，删除文档时级联清理片段 |

---

## 九、待确认

1. 云端公共库由谁维护（谁有百炼账号的主控权）、Key 如何分发给另外两人
2. 「公共」是否需要做到老师/同学可匿名访问——若需要，方案要加回一个对外服务，与当前「不做穿透」冲突
3. 胡的采集输出能否稳定按第四节字段交付
